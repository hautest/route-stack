# 소개 {#introduction}

route-stack은 웹에서도 네이티브 앱 같은 내비게이션을 만들어 줍니다. 특히 앱의 웹뷰에 띄운 웹앱을 위해 만들었습니다. 지나온 screen은 모두 현재 screen 뒤에 마운트된 채로 남습니다. push하면 새 screen이 밀려 들어오고, back하면 그 screen이 밀려 나가면서 실제 이전 screen이 드러납니다. iOS에서는 화면 왼쪽 가장자리에서 끌거나 전체 스와이프로 돌아갈 수도 있습니다.

## 문제 {#the-problem}

라우터는 한 번에 페이지 하나만 렌더합니다. 목록에서 상세 페이지로 가면 목록은 언마운트되고, 돌아오면 처음부터 다시 렌더됩니다. 데이터를 다시 받아 오고, 스크롤 위치는 늦게 복원되며, 입력값은 사라집니다. 두 페이지 사이에 애니메이션을 넣기 어려운 것도 같은 이유입니다. 새 페이지가 나타날 때 이전 페이지는 이미 사라진 뒤입니다.

흔히 쓰는 해법은 View Transition API입니다. 이전 페이지를 캡처하고 새 페이지를 렌더한 뒤, 두 캡처 사이를 애니메이션합니다. 하지만 screen을 쌓아 가는 구조의 앱에는 부족합니다.

- 이전 페이지는 DOM이 바뀌기 전에 캡처해야 하는데, DOM을 바꾸는 시점이 라우터마다 다릅니다.
- 전환을 준비하는 동안 렌더가 멈춥니다. 새 페이지가 느리면 그동안 화면이 얼어붙습니다.
- 스와이프하는 동안 뒤에 보이는 페이지는 캡처한 이미지라서, 그 페이지에서 데이터가 로드되어도 화면에는 보이지 않습니다.
- 전환은 문서당 하나만 실행되는데, React도 자체 전환을 시작합니다.

## 접근 방식 {#the-approach}

route-stack은 screen을 캡처하지 않고 screen 자체를 보관합니다.

- **screen이 살아 있습니다.** 떠난 screen은 React의 `<Activity>`로 숨긴 채 DOM에 남겨 둡니다. 상태, 입력값, 스크롤이 그대로 유지되고, effect는 screen이 다시 보일 때까지 멈춥니다.
- **살아 있는 두 screen이 움직입니다.** push, back, 스와이프 모두 두 screen을 화면 크기의 레이어로 띄우고 Web Animations API로 애니메이션합니다. `transform`과 `opacity`만 쓰며, 애니메이션은 합성 스레드에서 실행됩니다.
- **history가 결정합니다.** 각 항목이 어떤 screen을 보여 줄지, 이동이 push인지 back인지 replace인지는 라우터가 아니라 브라우저 history로 판단합니다. 그래서 어떤 라우터를 쓰든 똑같이 동작합니다.
- **라우터는 그대로입니다.** 라우트, loader, 링크를 지금처럼 씁니다. 어댑터는 라우터가 렌더한 경로를 스택에 알려 주는 일만 합니다.

## 언제 쓰나 {#when-to-use-it}

- iOS나 Android 웹뷰에 띄운 웹앱이 그 웹뷰를 품은 네이티브 앱처럼 느껴져야 할 때
- back이 즉시 반응하고 페이지가 그대로 남아 있어야 하는 모바일 우선 웹앱

쓰지 않는 게 나은 경우:

- 데스크톱 사이트, 또는 사용자가 브라우저 자체의 스와이프 백을 기대하는 사이트: 자세한 내용은 [제약](/ko/reference/limitations)에 있습니다.
- 요소 단위 공유 전환(사진이 커지면서 다음 페이지로 이어지는 방식): route-stack은 screen 전체를 움직입니다.
