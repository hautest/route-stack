# 스와이프 백 {#swipe-back}

스와이프 백은 플랫폼마다 기본 동작이 다릅니다. iOS에서는 화면 왼쪽 가장자리에서 끌어 뒤로 갑니다. Android에서는 시스템 뒤로가기를 쓰므로 기본으로 꺼져 있습니다. 전환 애니메이션도 iOS와 Android 각각의 기본 전환을 따릅니다. `swipe="full"`을 지정하면 두 플랫폼 모두 전체 스와이프를 쓸 수 있습니다.

전환 애니메이션은 플랫폼 기능이 아니라 웹 애니메이션으로 동작합니다. 그래서 플랫폼에 묶이지 않고 원하면 Android에서 iOS 전환을 쓰거나 그 반대로 고를 수 있습니다([전환](./transitions) 참고).

끄는 동안 screen이 손가락을 따라 움직이고 그 뒤로 이전 screen이 보입니다. 캡처한 이미지가 아니라 실제로 동작하는 screen입니다. 손을 떼면 뒤로 갈지 제자리로 돌아올지 정해집니다.

## `swipe` prop {#the-swipe-prop}

```tsx
<Stack>                 // 생략: iOS 등은 "edge", Android는 false
<Stack swipe="edge">    // 모든 플랫폼에서 edge (Android도 켜짐)
<Stack swipe="full">    // 모든 플랫폼에서 전체 스와이프
<Stack swipe={false}>   // 모든 플랫폼에서 끔
```

| `swipe`  | iOS                                           | Android        |
| -------- | --------------------------------------------- | -------------- |
| (기본값) | 가장자리에서                                  | 없음           |
| `"edge"` | 가장자리에서                                  | 가장자리에서¹  |
| `"full"` | 전체 스와이프                                 | 전체 스와이프¹ |
| `false`  | 없음                                          | 없음           |
| 함수     | back마다 경로로 판단합니다([화면별 스와이프 설정](#per-screen)) |                |

- ¹ 자세한 내용은 [Android](#android)에 있습니다.
- `animate`가 `false`를 반환하는 back에도 스와이프가 없습니다. 손가락을 따라갈 슬라이드가 없기 때문입니다.
- 스와이프가 없는 곳에서도 뒤로가기 버튼과 history back은 그대로 동작하고 애니메이션도 재생됩니다.

데모 위쪽 선택 상자로 하나씩 바꿔 볼 수 있습니다.

## Android {#android}

Android의 제스처 내비게이션에서는 화면 왼쪽과 오른쪽 가장자리를 밀면 시스템 뒤로가기가 됩니다. 이 터치는 운영체제가 먼저 가져갑니다. 그래서 `"edge"`를 지정해도 스택의 스와이프는 시작되지 않고 시스템 뒤로가기가 동작합니다. 스택이 Android에서 스와이프를 기본으로 꺼 두는 이유입니다. 시스템 뒤로가기도 `history.back()`으로 처리되므로 back 전환은 그대로 재생됩니다.

Android에서도 스와이프를 쓰려면 `swipe`를 지정해야 합니다. 버튼 내비게이션을 쓰는 기기에서는 `"edge"`가 동작합니다. 제스처 내비게이션을 쓰는 기기에서는 화면 가운데서 시작하는 드래그(`"full"`)만 스택이 받습니다.

## 전체 스와이프 {#from-anywhere-on-the-screen}

```tsx
<Stack swipe="full">
```

iOS 26 앱의 화면 전체 뒤로가기 제스처처럼, 전체 스와이프는 보이는 화면 어디서든 옆으로 끌어 뒤로 갑니다. 다만 가로 스크롤이나 슬라이더처럼 옆으로 끄는 요소 위에서는 그 요소가 드래그를 먼저 받습니다. 가로 스크롤은 맨 앞까지 스크롤한 뒤 다시 끌면 스와이프 백이 됩니다([페이지에 남기는 드래그](#what-the-page-keeps) 참고).

앱의 가로 제스처를 스택이 구분할 수 있을 때 쓰는 것을 권합니다. 네이티브 가로 스크롤과 컨트롤은 구분되지만, JS로 움직이는 캐러셀이나 드로어는 따로 선언하지 않으면 스와이프와 함께 움직입니다([JS로 만든 제스처](#js-gestures) 참고). 그런 제스처가 많은 screen에서는 함수로 그 screen만 가장자리 스와이프로 남기는 게 좋습니다.

## 화면별 스와이프 설정 {#per-screen}

`swipe`에 함수를 넘기면 screen마다 스와이프 방식을 다르게 정할 수 있습니다. 스택은 스와이프를 열지 판단할 때마다 이 함수를 호출합니다. 지금 보이는 screen의 경로(`from`)와 스와이프로 돌아갈 screen의 경로(`to`)를 넘기면 함수는 `"edge"`, `"full"`, `false` 중 하나를 돌려줍니다.

```tsx
<Stack
  swipe={(from, to) => {
    // 결제·편집 화면: 실수로 나가지 않게 끔
    if (from.startsWith("/checkout") || from.startsWith("/editor")) return false;
    // 지도: 지도를 옆으로 끄는 동작과 겹치지 않게 가장자리만
    if (from.startsWith("/map")) return "edge";
    return "full";
  }}
>
```

- `false`를 돌려주면 그 screen에서는 스와이프가 꺼지고 터치는 그대로 페이지가 받습니다.
- 함수는 경로만 보고 판단해야 합니다. 편집 중인 폼처럼 페이지 안의 상태가 바뀌어도 스택은 이 함수를 다시 호출하지 않습니다. 작성 중인 내용이 있을 때 떠나지 못하게 하려면 라우터의 blocker를 쓰면 됩니다([back을 붙잡는 라우터](#routers-that-hold-a-back) 참고).
- Next.js에서는 Client Component에서 함수를 넘겨야 합니다([라우터](./routers#next-js-app-router) 참고).

## 제스처 {#the-gesture}

스와이프는 다음 순서로 판단합니다.

1. **시작 위치:** edge 스와이프(`swipe="edge"`)에서는 보이는 screen 위, 창 왼쪽 끝 20px 안에서 시작한 터치만 받습니다. 전체 스와이프(`swipe="full"`)에서는 보이는 screen 어디서 시작해도 받습니다.
2. **스와이프 시작:** 손가락이 10px 움직였을 때 위아래보다 오른쪽으로 더 많이 움직였으면 스와이프가 시작됩니다.
3. **뒤로 가기:** 오른쪽 끝까지 남은 거리의 40%를 지나서 손을 떼거나, 마지막 100ms 동안 1px/ms보다 빠르게 움직였으면 뒤로 갑니다.
4. **제자리로 돌아오기:** 그 밖의 경우에는 제자리로 돌아옵니다. 시스템이 터치를 가져가거나(`touchcancel`) 두 번째 손가락이 닿을 때도 마찬가지입니다.
5. **손을 뗀 뒤:** 남은 슬라이드는 전환의 duration과 easing으로 재생합니다.

- 페이지 위에 덮는 요소가 없습니다. 가장자리를 탭하면 그 아래 버튼이 눌리고, 가장자리에서 세로로 끌면 스크롤됩니다.
- 스와이프가 시작된 뒤에는 손가락이 위아래로 흔들려도 그 아래 페이지가 스크롤되지 않습니다.
- 돌아갈 screen이 있을 때만 스와이프가 시작됩니다. 새로고침이나 딥링크로 막 열린 첫 screen에는 돌아갈 screen이 없으므로 스와이프할 수 없습니다(뒤로가기 버튼은 동작합니다).
- 전환이 재생되는 동안에는 스와이프가 시작되지 않습니다.
- 손을 떼면 다음 프레임에 `history.back()`이 호출되고, 라우터는 이를 다른 back과 똑같이 처리합니다.

## 페이지에 남기는 드래그 {#what-the-page-keeps}

손가락이 10px 움직였고 위아래보다 오른쪽으로 더 많이 움직였으면, 스택은 손가락이 처음 닿은 요소를 확인합니다. 다음 경우에는 드래그를 페이지에 남깁니다.

| 손가락 아래                                                                                  | 가장자리 | 가장자리 밖 |
| -------------------------------------------------------------------------------------------- | -------- | ----------- |
| 옆으로 끄는 컨트롤: 범위 슬라이더, `video`와 `audio`, `role="slider"`나 `role="scrollbar"`   | 페이지   | 페이지      |
| `data-stack-no-swipe`를 단 요소, 또는 그 안                                                  | 페이지   | 페이지      |
| 텍스트: 텍스트 입력, `textarea`, `select`, `contenteditable`(끌면 커서나 선택 영역이 움직입니다) | 스와이프 | 페이지      |
| `pan-x` 없이 `touch-action`을 선언한 요소(`pan-y`, `none`. `auto`와 `manipulation`은 해당 없음), 또는 그 안 | 스와이프 | 페이지      |
| 아직 왼쪽으로 스크롤할 수 있는 가로 스크롤 영역                                              | 스와이프 | 페이지      |
| 맨 앞에 있는 가로 스크롤 영역, 그 밖의 모든 것                                               | 스와이프 | 스와이프    |

- 가로 스크롤 영역이 맨 앞이면 더 스크롤할 곳이 없으므로 스와이프로 뒤로 갑니다. 네이티브 스크롤 뷰가 끝에 닿았을 때와 같습니다. 가장자리에서는 네이티브 가장자리 제스처처럼 텍스트, 가로 스크롤, 선언된 제스처보다 스와이프가 우선합니다.
- 실제로 손가락이 닿은 요소를 봅니다. 웹 컴포넌트 안의 슬라이더처럼 shadow root 안에 있어도 마찬가지입니다.
- 보이는 screen만 봅니다. `<body>`로 띄운 시트나 모달처럼 screen 밖에 있는 요소를 터치하면 스와이프가 시작되지 않습니다. 스택 바깥 조상에 단 것도 읽지 않으므로, 앱 루트의 `touch-action: pan-y`나 `data-stack-no-swipe` 때문에 스와이프가 꺼지지 않습니다.
- 두 손가락으로 확대한 상태에서는 드래그를 페이지에 남깁니다. 확대된 화면을 옆으로 옮겨 보는 동작입니다.
- 체크박스, 라디오 버튼, 버튼은 누르기만 하는 컨트롤이라 그 위에서 끌어도 스와이프됩니다.

### JS로 만든 제스처 {#js-gestures}

JS로 요소를 움직이는(`transform`) 캐러셀이나 드로어는 스택이 알아볼 방법이 없습니다. 아무 선언이 없으면 그 요소와 스와이프가 함께 움직입니다. 다음 중 하나로 선언해야 합니다.

```css
.carousel {
  touch-action: pan-y; /* 세로 스크롤은 브라우저가, 가로 드래그는 이 요소가 처리 */
}
```

```html
<div data-stack-no-swipe>…</div>
```

대부분의 캐러셀 라이브러리(Swiper, Embla)는 `touch-action`을 이미 달아 둡니다. `data-stack-no-swipe`는 그 요소 위에서 가장자리 스와이프까지 끕니다.

## 비용 {#cost}

브라우저가 스크롤을 시작하기 전에 드래그를 가져오려고, 스택은 스와이프를 시작할 수 있는 동안(돌아갈 screen이 있고, 전환이 재생 중이 아니고, `swipe`와 `animate`가 그 back을 허용할 때) passive가 아닌 `touchmove` 리스너를 붙여 둡니다. 가장자리 스와이프만 켠 경우에도 마찬가지입니다. 그러면 브라우저는 스크롤을 시작하기 전에 페이지의 처리를 기다립니다. 첫 screen에는 이 리스너가 없습니다.

iPhone 15 Pro(WKWebView)와 Galaxy S24(Android WebView)에서 한 번씩 측정한 결과는 다음과 같습니다.

- 페이지가 유휴 상태일 때: 리스너가 없을 때와 차이가 없었습니다.
- 메인 스레드를 일부러 바쁘게 만들었을 때(80ms마다 40ms): Galaxy에서 스크롤 시작이 약 10ms 늦어졌습니다. iPhone에서는 차이를 구분할 수 없었습니다.

## back을 붙잡는 라우터 {#routers-that-hold-a-back}

라우터가 back을 거부하면("이 페이지를 떠나시겠어요?"라고 묻는 blocker) screen은 제자리로 돌아갑니다. 그 뒤 사용자가 떠나기를 선택하면 별도의 back으로 처리되고, 그 back의 전환이 재생됩니다. React Router와 TanStack Router의 blocker를 지원합니다.

## iOS Safari(브라우저) {#ios-safari-the-browser}

Safari 브라우저에서는 자체 가장자리 스와이프가 스택의 스와이프와 함께 동작합니다. 자세한 내용은 [트러블슈팅](/ko/reference/troubleshooting#ios-safari-two-swipes)에 있습니다.
